Diagramas de Classe com UML

Modelando um E-commerce

Vamos aprender a mapear as regras de negócio de uma loja virtual, abordando desde a estrutura básica de uma entidade até os relacionamentos mais complexos como Composição e Interfaces.

Estrutura

📦 1. A Anatomia de uma Entidade

Uma classe é dividida em 3 compartimentos: Nome (Identificador), Atributos (Dados/Estado) e Métodos (Ações/Comportamento).

classDiagram class Produto { + string nome + float preco + int estoque + aplicarDesconto(porcento) + atualizarEstoque(qtd) }
Segurança

🔒 2. Visibilidade (Encapsulamento)

Garante que dados sensíveis não sejam alterados indevidamente:

  • + Public: Acesso livre.
  • - Private: Acesso apenas interno à classe.
  • # Protected: Acesso pela classe e suas herdeiras.
classDiagram class ContaCliente { + string email - string senhaHash # float pontosFidelidade + fazerLogin(senha) - validarToken() }
Matemática

🔢 3. Cardinalidade (Multiplicidade)

Define quantos objetos estão envolvidos. Um Cliente pode realizar de 0 a muitos (0..*) Pedidos. Mas um Pedido pertence a exatamente 1 Cliente.

classDiagram Cliente "1" --> "0..*" Pedido : realiza
Relacionamento

🔗 4. Associação (O Básico)

Uma classe interage com a outra, mas são independentes. Não há "posse". Exemplo: O Cliente pede ajuda no chat para um Atendente.

classDiagram class Cliente { + abrirChamado() } class Atendente { + responder() } Cliente --> Atendente : solicita ajuda
Relacionamento

🤍 5. Agregação (Dependência Fraca)

O Todo agrupa a Parte, mas a Parte sobrevive sozinha. Representado pelo losango vazado.

Se o CarrinhoCompras for esvaziado, o Produto continua existindo normalmente na loja.

classDiagram class CarrinhoCompras { + float valorTotal } class Produto { + string nome } CarrinhoCompras o-- Produto : agrupa (0..*)
Relacionamento

🖤 6. Composição (Dependência Vital)

A Parte morre se o Todo for destruído. Representado pelo losango preenchido.

Se uma compra for cancelada e o Pedido deletado, os registros dos ItensDoPedido devem ser destruídos junto, pois não fazem sentido sozinhos.

classDiagram class Pedido { + dataCriacao } class ItemPedido { + int quantidade } Pedido *-- ItemPedido : compõe (1..*)
Arquitetura

🧬 7. Herança (Generalização)

Relação "É um". Classes filhas herdam características da mãe. Um Produto Físico (com frete) e um Produto Digital (com link) são Produtos.

classDiagram class Produto { + string nome + float preco } class ProdFisico { + float peso } class ProdDigital { + string linkDownload } Produto <|-- ProdFisico Produto <|-- ProdDigital
Arquitetura

🔌 8. Realização (Interfaces)

Uma Interface é um Contrato. Ela diz "o que" fazer, mas não "como". Classes assinam o contrato prometendo implementá-lo.

classDiagram class IPagamento { <<interface>> + processar(valor) } class Pix { + string chave + processar(valor) } class Cartao { + string numCartao + processar(valor) } IPagamento <|.. Pix : implementa IPagamento <|.. Cartao : implementa
Conclusão

🌐 9. O Ecossistema Completo
